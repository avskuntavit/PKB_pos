# FoodPOS

ระบบ POS ร้านอาหาร (หน้าร้าน + หลังบ้าน) เขียนด้วย **Laravel 12 + Inertia 2 + Vue 3 + Tailwind CSS v4**
โครงสร้างและชุดรายงานอ้างอิงจากระบบ Back Office ของร้านอาหารทั่วไป (ยอดขาย, ภาษี, สินค้าคงคลัง,
ลูกค้า, รอบการขาย, โปรโมชั่น, Voucher, พนักงาน, โต๊ะ)

---

## ติดตั้ง

```bash
composer install
npm install

cp .env.example .env
php artisan key:generate

# ตั้งค่า DB ใน .env แล้ว
php artisan migrate --seed

npm run dev      # หรือ npm run build สำหรับ production
php artisan serve
```

> ถ้าอยากลองเล่นเร็ว ๆ โดยไม่ตั้ง MySQL ให้แก้ `.env` เป็น
> `DB_CONNECTION=sqlite` และ `touch database/database.sqlite`
> โค้ดรายงานรองรับทั้ง MySQL และ SQLite (ฟังก์ชันวันที่แยกตาม driver ให้แล้ว)

### บัญชีตัวอย่างหลัง seed

| บทบาท | อีเมล | รหัสผ่าน |
|---|---|---|
| เจ้าของร้าน | `owner@foodpos.test` | `password` |
| ผู้จัดการ | `manager1@foodpos.test` | `password` |
| แคชเชียร์ | `cashier00@foodpos.test` | `password` |

Seeder สร้าง 2 สาขา เมนูก๋วยเตี๋ยว/ข้าว/เครื่องดื่ม โต๊ะ 16 ตัวต่อสาขา
และ **ยอดขายย้อนหลัง 30 วัน** เพื่อให้หน้ารายงานมีข้อมูลจริงให้ดูทันที

`LiveDemoSeeder` ยังสร้างสถานการณ์ "กำลังขายอยู่ตอนนี้" ให้กดเล่นได้ทันที — ต่อสาขาจะได้
โต๊ะที่มีใบสั่งครัวค้างบน `/kitchen`, โต๊ะที่ลูกค้าสั่งเองรออนุมัติบน `/pos`,
และโต๊ะที่กดเรียกเก็บเงินไว้

### ลองฟลว์สมาชิกและสิทธิ์พนักงาน

1. ตั้ง `FOODPOS_OTP_EXPOSE=true` ใน `.env` (รหัส OTP จะขึ้นบนหน้าจอ)
2. เปิด `/order/login` ในหน้าต่างไม่ระบุตัวตน → ใส่เบอร์ → ใส่รหัสที่โชว์
3. ไป `/order/account` → "ขอสิทธิ์พนักงาน" → กรอกรหัสพนักงาน
4. ล็อกอินผู้จัดการอีกหน้าต่าง → `/backoffice/employees` → กดอนุมัติ
5. กลับไป `/order` จะเห็นราคาพนักงานบนเมนูและวงเงินคงเหลือของเดือนนี้
6. สั่งอาหาร → ดูส่วนลดที่ถูกหักในหน้าติดตาม
7. รับเงินที่ POS → `/backoffice/staff-benefit` จะมีตัวเลขให้บัญชีตั้งเบิก

### ลองฟลว์หน้าร้านออนไลน์

1. เปิด `/order` ในหน้าต่างไม่ระบุตัวตน (จะได้เป็นลูกค้าจริง ๆ ไม่ใช่พนักงาน)
2. สั่งอาหาร → เลือก "พร้อมเพย์" → จะเห็น QR พร้อมยอดบนหน้าติดตาม
3. ล็อกอินพนักงานอีกหน้าต่าง เปิด `/pos/online-orders` → เห็นใบรอกดรับ
4. กด "รับออเดอร์" → ใบสั่งครัวโผล่ที่ `/kitchen` และหน้าติดตามของลูกค้าขยับเอง
5. ลองเปิด `/order` ในหน้าต่างที่ล็อกอินพนักงานอยู่ จะเห็นแถบโหมดพนักงานสั่งแทน

### ลองฟลว์ลูกค้าสแกนสั่งเอง

1. เข้า `/backoffice/tables/qr` → เห็น QR ทุกโต๊ะ (กดพิมพ์ได้)
2. สแกนด้วยมือถือ หรือก๊อปลิงก์ `/t/{token}` เปิดในหน้าต่างไม่ระบุตัวตน
3. สั่งอาหาร → เปิดหน้า `/pos` ด้วยบัญชีพนักงาน จะเห็นแผงรอยืนยัน
4. กดยืนยัน → ใบสั่งครัวโผล่ที่ `/kitchen` ทันที

## จุดออกแบบที่ควรรู้

**1. `business_date` ไม่ใช่ `created_at`**
ร้านอาหารขายข้ามเที่ยงคืนได้ ทุกรายงานจึงอิง `business_date` ที่คำนวณจาก
`branches.business_day_start` (ค่าเริ่มต้น 05:00) — บิลตอนตี 2 ยังนับเป็นยอดของเมื่อวาน

**2. ยอดเงินเก็บครบทุกชั้นในตาราง `orders`**
`subtotal / item_discount / bill_discount / service_charge / tax_amount / rounding / grand_total`
เก็บแยกคอลัมน์ ทำให้ย้อนดูรายงานเก่าได้ตรงกับที่พิมพ์ใบเสร็จ แม้ภายหลังจะแก้ราคาสินค้าหรือเรต VAT

**3. รายการในบิลเก็บ snapshot**
`order_items.product_name / category_name / unit_price / unit_cost` ก๊อปไว้ตอนขาย
แก้ชื่อเมนูภายหลังไม่ทำให้รายงานย้อนหลังเพี้ยน

**4. การคำนวณยอดอยู่ที่เดียว**
`OrderService::recalculate()` เท่านั้น ลำดับคือ
ยอดขาย → ลดรายสินค้า → ลดท้ายบิล/โปรฯ/Voucher → ค่าบริการ → ค่าจัดส่ง → ภาษี → ปัดเศษ
ถ้าจะเพิ่มส่วนลดแบบใหม่ ให้เติมในนี้ที่เดียว

**5. VAT รวมในราคาเป็นค่าเริ่มต้น**
`branches.vat_included = true` → แยกภาษีออกมาโชว์ ไม่บวกเพิ่ม (`Money::extractVat`)
ถ้าร้านคิด VAT นอก ให้ตั้งเป็น `false` ระบบจะบวกภาษีทับ

**6. ไม่มีการลบข้อมูลการขายจริง**
ยกเลิกรายการ = `status = 'void'` / ทำลายบิล = `orders.status = 'void'`
เพื่อให้ตรวจสอบย้อนหลังและทำรายงาน "บิลที่ยกเลิก" ได้

**7. Multi-branch มาตั้งแต่ต้น**
ทุกตารางหลักมี `branch_id` + trait `BelongsToBranch` เติมให้อัตโนมัติ
`ResolveCurrentBranch` middleware ตัดสินสาขาจาก query → session → สาขาของ user
เจ้าของร้านดูรวมหลายสาขาได้ คนอื่นถูกจำกัดที่สาขาตัวเอง

## ลูกค้าสแกนสั่งเอง (Self-ordering)

### ฟลว์เต็ม

```
ลูกค้าสแกน QR ที่โต๊ะ
   └─ GET /t/{qr_token}
        └─ ResolveTableSession middleware
             ├─ หา DiningTable จาก qr_token
             ├─ มี table_session ที่ active อยู่แล้ว → ใช้ต่อ
             └─ ไม่มี → เปิดรอบใหม่ (เกาะบิลที่พนักงานเปิดไว้ ถ้ามี)

ลูกค้าเลือกเมนู → กดยืนยัน
   └─ POST /t/{qr_token}/orders
        └─ SelfOrderService::submit()
             ├─ ยังไม่มีบิล → เปิดบิลให้ (source = self_order)
             ├─ สร้าง order_items: status=pending, approval_status=pending
             └─ ยังไม่เข้าครัว

พนักงานเห็นแผงแจ้งเตือนบนหน้า POS → กดยืนยัน
   └─ POST /pos/orders/{order}/approve
        └─ SelfOrderService::approve()
             ├─ approval_status = approved, status = sent
             └─ KitchenService::createTickets() → ใบสั่งครัวขึ้น KDS ทันที

ลูกค้าสั่งเพิ่มได้เรื่อย ๆ (วนซ้ำขั้นตอนด้านบน)

ลูกค้ากด "เรียกพนักงานเก็บเงิน"
   └─ POST /t/{qr_token}/call  → service_calls
        └─ ขึ้นแถบแจ้งเตือนสีส้มบนหน้า POS ทุกเครื่อง

พนักงานเก็บเงิน → PaymentService::pay()
   └─ ปิด table_session อัตโนมัติ
        └─ ลิงก์เดิมสั่งต่อไม่ได้ / โต๊ะถัดไปสแกน QR เดิมได้รอบใหม่ทันที
```

### ทำไม QR ถึงเป็นแบบถาวรต่อโต๊ะ

พิมพ์ครั้งเดียวติดไว้ที่โต๊ะตลอด ไม่ต้องพิมพ์ใหม่ทุกวันหรือทุกบิล
ความปลอดภัยไม่ได้อยู่ที่การเปลี่ยน QR แต่อยู่ที่ 4 ชั้นนี้:

1. `qr_token` สุ่ม 40 ตัวอักษร เดาไม่ได้
2. `table_sessions` ปิดอัตโนมัติเมื่อบิลถูกชำระ — ลิงก์เก่าสั่งไม่ได้
3. ทุกรายการที่ลูกค้าสั่งต้องให้พนักงานกดยืนยันก่อนเข้าครัว (ชั้นนี้สำคัญที่สุด)
4. `throttle` ที่ route — สั่ง 20 ครั้ง/นาที, เรียกพนักงาน 10 ครั้ง/นาที, polling 60 ครั้ง/นาที

ถ้าสงสัยว่า QR ถูกถ่ายรูปเอาไปใช้ข้างนอก กด **"ออก QR ใหม่"** ในหน้า `/backoffice/tables/qr`
token เดิมตายทันที แล้วพิมพ์แผ่นใหม่ไปเปลี่ยน

### ทำไมต้องรอพนักงานยืนยัน

เปิดให้เข้าครัวตรง ๆ ได้ (แก้ `OrderSource::SelfOrder::needsApproval()` ให้คืน `false`)
แต่ค่าเริ่มต้นเป็นการรอยืนยัน เพราะ:

- ของหมดระหว่างวันเป็นเรื่องปกติในร้านอาหาร — พนักงานคุมหน้างานรู้ก่อนระบบ
- เด็กกดเล่น / กดผิด / กดซ้ำ ไม่ทำให้ครัวทำของทิ้ง
- ปฏิเสธรายการเดียวได้โดยไม่ต้องทำลายทั้งบิล

รายการที่ถูกปฏิเสธจะถูก `void` และหายจากยอดบิลทันที (ไม่ลบทิ้ง — ยังตรวจย้อนหลังได้)

### สมาชิกและโปรโมชั่น

ลูกค้าที่สั่งผ่าน QR ไม่ได้ล็อกอิน บิลจึงไม่มี `customer_id` →
**ไม่ได้แต้มสะสม และใช้โปรโมชั่นเฉพาะสมาชิกไม่ได้** (`PaymentService::awardPoints()` ข้ามไปเลย)

หน้าลูกค้าบอกเรื่องนี้ไว้ตั้งแต่บนสุดของหน้าจอ ไม่ให้ไปรู้ตอนจ่ายเงิน
ถ้าลูกค้าอยากได้แต้ม ให้แจ้งพนักงานผูกเบอร์ตอนชำระเงิน — บิลนั้นจะได้แต้มตามปกติ

### กันยอดเพี้ยนตอนเก็บเงิน

เคสที่เจอจริง: พนักงานกำลังกดรับเงิน ลูกค้ากดสั่งน้ำเพิ่มพอดี
ระบบบล็อกไว้ทั้งสองชั้น — ปุ่มชำระเงินบนหน้า POS จะกดไม่ได้
และ `PaymentService::pay()` โยน `DomainException` ถ้ายังมีรายการรอยืนยันค้างอยู่

## หน้าร้านออนไลน์ (สั่งล่วงหน้า)

หน้าเดียวที่ `/order` ใช้ได้ทั้งลูกค้าและพนักงาน ระบบดูจาก `auth()` เอง ไม่มี URL แยก
รูปแบบการใช้งานตามแบบแอปสั่งอาหารทั่วไป — ปกร้าน, ป้ายเปิด/ปิด, ค้นหา, แถบหมวดหมู่ที่เลื่อนตาม,
การ์ดเมนูพร้อมรูป, แถบตะกร้าลอยด้านล่าง แล้วไปตะกร้า → เช็คเอาต์ → หน้าติดตาม

### ฟลว์ลูกค้า

```
เปิด /order  (หรือ /order/{รหัสสาขา})
   └─ เลือกเมนู → ตะกร้า → เช็คเอาต์
        ├─ รับอาหารแบบไหน: สั่งล่วงหน้ารับที่ร้าน / ทานที่ร้าน (จองล่วงหน้า)
        ├─ ชื่อ + เบอร์ (ไม่มี OTP)
        ├─ เวลาที่จะมารับ — ตั้งต้นที่เร็วสุดเท่าที่ครัวทำทัน (branches.prep_minutes)
        └─ วิธีจ่าย: จ่ายตอนรับ / พร้อมเพย์ / คนละครึ่ง / ไทยช่วยไทย
   └─ กดยืนยัน → เด้งไป /order/track/{token}

ร้านเห็นใบใหม่ที่ /pos/online-orders (เด้งขึ้นบนสุด สีเหลือง)
   ├─ กด "รับออเดอร์" → รายการเข้าครัวทันที ใบสั่งครัวขึ้น KDS
   └─ กด "ปฏิเสธ" + เหตุผล → บิลถูก void และลูกค้าเห็นเหตุผลบนหน้าติดตามทันที

ครัวทำเสร็จ → พนักงานกด "พร้อมให้รับ" → ลูกค้าเห็นสถานะเปลี่ยนเองภายใน 10 วินาที
ลูกค้ามารับ → พนักงานรับเงินที่ POS → ออเดอร์ปิดงานอัตโนมัติ
```

### โหมดพนักงานสั่งแทน

พนักงานที่ล็อกอินอยู่แล้วเปิด `/order` จะเห็นแถบสีฟ้าเพิ่มขึ้นมาด้านบน:
เลือกโต๊ะได้ และมีข้อความบอกว่าออเดอร์นี้จะเข้าครัวทันที

| | ลูกค้าสั่งเอง | พนักงานสั่งแทน |
|---|---|---|
| ต้องรอร้านกดรับ | ใช่ | ไม่ — ถือว่ารับแล้ว เข้าครัวทันที |
| `orders.source` | `online` | `pos` |
| เลือกโต๊ะได้ | ไม่ | ได้ |
| สั่งนอกเวลาทำการ | ไม่ได้ | ได้ (เขายืนอยู่หน้าร้านจริง) |
| บันทึกว่าใครสั่ง | – | `orders.placed_by_user_id` |

ใช้ตอนรับออเดอร์ทางโทรศัพท์ หรือเดินถือมือถือรับออเดอร์ที่โต๊ะ โดยไม่ต้องกลับไปที่เครื่อง POS

### เรื่องเบอร์โทรกับแต้มสะสม

ไม่มี OTP ตามที่ตกลงกันไว้ **เบอร์จึงเป็นช่องทางติดต่อ ไม่ใช่การยืนยันตัวตน**
แต่ระบบยังผูกออเดอร์กับ `customers` ตามเบอร์ให้ และให้แต้มตอนชำระเงิน
เหตุผลคือคนที่มารับของยืนอยู่ตรงหน้าพนักงานอยู่แล้ว — ต่างจากการสั่งที่โต๊ะผ่าน QR ที่ไม่มีเบอร์เลย

ร้านที่ไม่สบายใจ ปิดได้ที่ `branches.award_points_online = false`
(มีเทสคุมทั้งสองทางแล้ว)

### วิธีชำระเงิน

ทั้งหมดนี้เป็นแค่ **"ความตั้งใจจะจ่าย"** (`orders.payment_intent`) ที่ลูกค้าเลือกตอนสั่ง
เงินเข้าจริงตอนพนักงานกดรับเงินที่ POS ซึ่งเป็นคนละเรื่องกัน

| ตัวเลือก | เกิดอะไรขึ้น |
|---|---|
| จ่ายตอนมารับ | ไม่มีอะไรพิเศษ — พนักงานรับเงินที่เคาน์เตอร์ตามปกติ |
| พร้อมเพย์ | หน้าติดตามแสดง **QR พร้อมเพย์ที่มียอดเงินฝังอยู่** ให้สแกนจ่ายล่วงหน้าได้เลย |
| คนละครึ่ง / ไทยช่วยไทย | แจ้งร้านไว้ล่วงหน้า หน้าคิวของพนักงานติดป้ายว่าต้องออก QR โครงการที่เคาน์เตอร์ |

### เงินเข้าจริงตอนไหน — พนักงานเป็นคนกดยืนยันเสมอ

**ระบบนี้ไม่ได้ต่อกับระบบชำระเงินใด ๆ** ไม่ว่าจะธนาคารหรือแอปของโครงการรัฐ
`payment_intent` เป็นแค่ปุ่มให้ลูกค้า *แจ้งล่วงหน้า* ว่าจะจ่ายด้วยวิธีไหน — ไม่ได้ตัดเงิน
ไม่ได้ตรวจสิทธิ์ ไม่ได้คำนวณส่วนที่รัฐช่วยจ่าย และไม่ทำให้บิลปิดเอง (มีเทสคุมข้อนี้ไว้)

สิ่งที่ระบบทำให้คือ**เอาข้อมูลไปวางตรงหน้าคนที่ต้องตัดสินใจ**:

```
ลูกค้าเลือกวิธีจ่ายตอนสั่ง
   └─ บันทึกลง orders.payment_intent

พนักงานเห็นป้ายบนการ์ดใน /pos/online-orders
   └─ "คนละครึ่ง — ออก QR ที่เคาน์เตอร์"

ลูกค้ามาถึง → กดปุ่ม "รับเงิน" บนการ์ด → เด้งไปหน้าจอขายของบิลนั้น
   └─ แบนเนอร์ฟ้าบอก "ลูกค้าแจ้งไว้ว่าจะจ่ายผ่านคนละครึ่ง"
   └─ ช่องทางจ่ายถูกเลือกไว้ให้ตรงแล้ว ไม่ต้องหาเอง

พนักงานออก QR ของโครงการ → ลูกค้าสแกน → เห็นรายการสำเร็จในแอปโครงการ
   └─ กลับมาติ๊ก "ยืนยันว่าเห็นรายการสำเร็จแล้วด้วยตาตัวเอง"
   └─ กด "ยืนยันรับเงินแล้ว"  ← เงินถูกบันทึกตรงนี้เท่านั้น
```

ช่องติ๊กยืนยันจะบังคับเฉพาะช่องทางที่ระบบมองไม่เห็นเงินเข้า (โครงการรัฐและพร้อมเพย์)
ถ้าไม่ติ๊ก ปุ่มยืนยันจะกดไม่ได้ — ตั้งใจให้เป็นการตัดสินใจของคน ไม่ใช่การกดผ่าน ๆ

**แบ่งจ่ายหลายช่องทางใช้ split payment ที่มีอยู่แล้ว** เช่น ยอด 100 บาท
โครงการช่วย 50 ลูกค้าจ่ายสดอีก 50 → บันทึกเป็น 2 บรรทัด
(`khon_la_khrueng` 50 + `cash` 50) พร้อมใส่เลขอ้างอิงจากแอปโครงการได้
รายงานจะแยกยอดสองช่องทางให้เอง ไม่ยุบเป็นก้อนเดียว

### QR พร้อมเพย์สร้างเองในระบบ

`PromptPayService` สร้าง payload ตามมาตรฐาน EMVCo QR (Merchant-Presented) เอง
ไม่ต้องลง package เพิ่ม ไม่ต้องยิงข้อมูลร้านออกไปที่ไหน แล้ววาดเป็นภาพ QR ฝั่งเบราว์เซอร์

- เบอร์มือถือ 10 หลัก → แปลงเป็น `0066xxxxxxxxx` (tag 01)
- เลขประจำตัว 13 หลัก → tag 02 / e-Wallet 15 หลัก → tag 03
- ระบุยอด → QR แบบใช้ครั้งเดียว (`01` = `12`), ไม่ระบุยอด → QR ถาวร (`11`)
- ปิดท้ายด้วย CRC-16/CCITT-FALSE

ตั้งค่าที่ `branches.promptpay_id` และ `branches.promptpay_name`
(ชื่อร้านใน QR รองรับแค่ ASCII ระบบตัดอักษรไทยออกให้เอง ไม่ทำให้ QR พัง)

### สถานะที่ลูกค้าเห็น

`FulfilmentStatus` แยกจาก `OrderStatus` โดยตั้งใจ — อันหลังพูดถึงสถานะทางบัญชีของบิล
(เปิด/ปิด/ทำลาย) ส่วนอันนี้พูดถึง "ของถึงมือลูกค้าหรือยัง"

```
ส่งออเดอร์แล้ว → ร้านรับออเดอร์แล้ว → กำลังปรุงอาหาร → พร้อมให้มารับ → รับของเรียบร้อย
                         ↘ ร้านปฏิเสธออเดอร์ / ยกเลิกแล้ว
```

ทุกครั้งที่เปลี่ยนสถานะจะบันทึกลง `order_status_events` พร้อมเวลา
ใช้ทำไทม์ไลน์บนหน้าติดตาม และวัดย้อนหลังได้ว่าร้านตอบรับช้าแค่ไหน

ลูกค้ายกเลิกเองได้เฉพาะตอนที่ร้านยังไม่กดรับ หลังจากนั้นต้องโทรหาร้าน (มีปุ่มโทรให้บนหน้าติดตาม)

## สมาชิกและสิทธิ์พนักงานองค์กร

### ล็อกอินด้วยเบอร์ + OTP

ไม่มีหน้า "สมัครสมาชิก" แยก — ยืนยันเบอร์ครั้งแรกคือการสมัครไปในตัว
ลูกค้าที่ไม่อยากล็อกอินก็ยังสั่งได้เหมือนเดิม แค่ไม่ได้แต้มและสิทธิ์พนักงาน

ลูกค้ากับพนักงานร้านใช้ **guard คนละตัว** (`web` กับ `customer`)
พนักงานจึงเปิดหน้าร้านออนไลน์สั่งแทนลูกค้าได้โดยไม่หลุดจากระบบ POS

> **ระบบนี้ยังไม่ได้ต่อผู้ให้บริการ SMS** — `OtpService` ออกรหัสและตรวจรหัสให้ครบ
> แต่การส่งจริงต้องเสียบ `App\Contracts\OtpSender` ของผู้ให้บริการเอง
> ค่าเริ่มต้นใช้ `LogOtpSender` ที่เขียนรหัสลง `storage/logs/laravel.log`
>
> ตอนทดสอบ ตั้ง `FOODPOS_OTP_EXPOSE=true` ใน `.env` แล้วรหัสจะขึ้นบนหน้าจอเลย
> (ห้ามเปิดบน production)

การป้องกันมี 3 ชั้น: ขอรหัสได้ 5 ครั้ง/ชม./เบอร์ · เว้น 60 วินาทีก่อนขอซ้ำ ·
กรอกผิดเกิน 5 ครั้งรหัสตายทันที และรหัสถูกเก็บเป็น hash ไม่ใช่ตัวเลขตรง ๆ

### ผูกกับพนักงานในองค์กร

```
ลูกค้าล็อกอิน → หน้าบัญชี → กรอกรหัสพนักงาน → สถานะ "รอ HR อนุมัติ"
   └─ HR เปิด /backoffice/employees → ตรวจกับทะเบียนจริง → อนุมัติ/ปฏิเสธ
        └─ อนุมัติแล้วเห็นราคาพนักงานบนเมนูทันที
```

ระบบ **ไม่ได้ต่อกับฐานข้อมูล HR** จึงยืนยันตัวตนอัตโนมัติไม่ได้ —
คนที่รู้ว่ารหัสนี้เป็นของใครจริงคือ HR หน้าจึงเป็นการให้คนตัดสิน ไม่ใช่ระบบเดาเอง
พนักงานลาออกก็กด "ถอนสิทธิ์" ได้ โดยประวัติการใช้สิทธิ์เดิมยังอยู่ครบ

### ส่วนลดคิดยังไง

ลดเป็น **"ราคาพนักงาน" รายเมนู** (`products.staff_price`) ไม่ใช่ลดเปอร์เซ็นต์ทั้งบิล
เมนูที่ไม่ได้ตั้งราคาพนักงานไว้จะไม่ถูกลดเลย — ร้านคุมได้ว่าเมนูไหนให้สิทธิ์

| กติกา | ตั้งค่าที่ |
|---|---|
| เปิด/ปิดสิทธิ์ทั้งสาขา | `branches.staff_benefit_enabled` |
| เพดานวงเงินต่อคนต่อเดือน (0 = ไม่จำกัด) | `branches.staff_benefit_monthly_cap` |
| ไม่ให้สิทธิ์กับแอลกอฮอล์ | `branches.staff_benefit_exclude_alcohol` + `products.is_alcohol` |
| ราคาพนักงานรายเมนู | `products.staff_price` |

ถ้าส่วนลดรอบนี้ทะลุเพดาน ระบบจะลดให้**เท่าที่เหลือ** แล้วส่วนที่เกินลูกค้าจ่ายเอง
ไม่ใช่ปฏิเสธทั้งบิล

### มูลค่าส่วนลด → ค่าใช้จ่ายสวัสดิการของบริษัท

ทุกบิลที่ใช้สิทธิ์จะบันทึกลง `staff_benefit_usages` ตอนชำระเงิน
เก็บ `period` เป็น `YYYY-MM` เพื่อ group ตามรอบเดือนได้ตรงไปตรงมา

`/backoffice/staff-benefit` สรุปให้สองตัวเลขที่บัญชีต้องใช้:

- **มูลค่าส่วนลด** = ส่วนที่บริษัทออกให้ → ตั้งเป็นค่าใช้จ่ายสวัสดิการ
- **ยอดที่จ่ายเอง** = เงินที่พนักงานจ่ายจริงที่ร้าน → เป็นรายได้ของร้านตามปกติ

ดาวน์โหลด CSV ได้ (มี BOM ให้ Excel ภาษาไทยอ่านออก)
บิลที่ถูกทำลายหรือคืนเงินเต็มจำนวนจะถูก **คืนวงเงิน** ให้พนักงานอัตโนมัติ

## ระบบคิว

เลขคิวรันใหม่ทุกวันขาย แยกตามสาขา — ลูกค้าจำ "คิว 12" ง่ายกว่าเลขบิลยาว ๆ

ออกเลขคิว **ตอนร้านกดรับออเดอร์** ไม่ใช่ตอนลูกค้ากดสั่ง
เพราะใบที่ถูกปฏิเสธไม่ควรกินเลขคิวไปเปล่า ๆ แล้วทำให้คิวกระโดด

- หน้าติดตามของลูกค้าบอกว่า "มีอีก N คิวก่อนหน้าคุณ"
- `/queue/{branch_code}` เป็นจอแสดงคิวหน้าร้าน ตัวเลขใหญ่ อ่านจากระยะ 3-5 เมตร
  แสดงแค่เลขคิวกับ**ชื่อต้น**เท่านั้น เพราะคนเดินผ่านก็เห็นจอนี้

## ประเมินความพึงพอใจ

ลูกค้าให้ดาวได้หลังชำระเงิน 1 บิลต่อ 1 ครั้ง เข้าถึงด้วย `track_token` ในลิงก์บิลนั้น
(คนที่ถือลิงก์ = คนที่สั่งบิลนี้) ไม่ต้องล็อกอินก็รีวิวได้

ถามดาวก่อนแล้วค่อยโชว์แท็ก — ให้ 5 ดาวแล้วเจอตัวเลือก "รอนาน" มันขัดกัน
หลังบ้านเห็นคะแนนเฉลี่ย การกระจาย 1-5 ดาว แท็กที่ถูกพูดถึงบ่อย และตอบกลับรีวิวได้

## ตั้งค่าสาขา

หน้าเดียวรวมทุกอย่างที่ต่างกันได้ระหว่างสาขา: ข้อมูลร้าน ภาษี ค่าบริการ การปัดเศษ
เวลาเปิดปิด พร้อมเพย์ สวัสดิการพนักงาน และช่องทางชำระเงิน

### ช่องทางชำระเงินต่อสาขา

ร้านนี้ไม่รับเงินสด Seeder จึงตั้งค่าเริ่มต้นไว้แบบนี้:

| ช่องทาง | สถานะ | ลูกค้าเลือกตอนสั่งล่วงหน้า |
|---|---|---|
| พร้อมเพย์ | เปิด | ได้ |
| คนละครึ่ง / ไทยช่วยไทย | เปิด | ได้ |
| โอนเงิน | เปิด | ไม่ (พนักงานเลือกเอง) |
| **เงินสด** | **ปิด** | – |
| บัตรเครดิต / e-Wallet / แอปเดลิเวอรี่ | ปิด | – |

ช่องทางที่ปิดไม่ใช่แค่ซ่อนปุ่ม — **เซิร์ฟเวอร์ปฏิเสธด้วย** ถ้ามีคนพยายามยิงเข้ามา
และหน้าตั้งค่ากันไม่ให้ปิดทุกช่องทางพร้อมกัน ไม่งั้นร้านจะรับเงินไม่ได้เลย

### จำกัดเวลาขายแอลกอฮอล์

ปิดไว้เป็นค่าเริ่มต้น เปิดแล้วตั้งช่วงเวลาได้หลายช่วง (รองรับช่วงคร่อมเที่ยงคืน)

> ระบบ**ไม่ได้ฝังกฎหมายไว้** — ร้านต้องตั้งช่วงเวลาเองให้ตรงกับระเบียบที่บังคับใช้อยู่
> เพราะระเบียบเปลี่ยนได้ และไม่ควรฝังไว้ในโค้ดที่แก้ยาก

## สูตร ส่วนผสม และต้นทุน

`/backoffice/recipes` ผูกวัตถุดิบเข้าเมนูพร้อมสัดส่วนต่อ 1 จาน สูตรทำสองหน้าที่:

1. **ตัดสต๊อกอัตโนมัติ** เมื่อขาย (เปิดด้วย `products.track_stock`)
2. **คำนวณต้นทุนจริง** แทนการเดาแล้วกรอกมือ

ต้นทุนตามสูตรคำนวณสดขณะพิมพ์ เห็นอัตรากำไรเปลี่ยนทันที
การซิงก์ต้นทุนเป็น **ทางเลือก** ไม่ใช่อัตโนมัติ เพราะบางร้านอยากกรอกเองเพื่อเผื่อของเสีย
มีปุ่ม "ซิงก์ต้นทุนทุกเมนู" ไว้ใช้ตอนราคาวัตถุดิบขยับทั้งกระดาน

### ปิดขายชั่วคราว (ของหมดวันนี้)

`products.unavailable_until` แยกจากการปิดเมนูถาวร (`is_active`) เพราะเป็นคนละเจตนา —
ของหมดคือเรื่องของวันนี้ พอถึงรอบวันถัดไปควรกลับมาขายเองโดยไม่ต้องมีใครจำ
เมนูที่ปิดจะหายจากทั้งหน้า POS และหน้าร้านออนไลน์

### รายงานต้นทุน–กำไรรายเมนู

ต้นทุนใช้ค่าที่ snapshot ไว้ใน `order_items.unit_cost` ตอนขาย
ไม่ใช่ต้นทุนวันนี้ — ถ้าใช้ต้นทุนปัจจุบัน กำไรของเดือนที่แล้วจะเปลี่ยนไปเรื่อย ๆ
ทุกครั้งที่วัตถุดิบขึ้นราคา หน้ายังไฮไลต์เมนูที่อัตรากำไรต่ำกว่า 30% ให้ด้วย

## สิทธิ์พนักงาน

ตำแหน่ง (เจ้าของ/ผู้จัดการ/แคชเชียร์/พนักงาน) เป็นแค่ **ชุดสิทธิ์ตั้งต้น**
สิทธิ์จริงของแต่ละคน = ค่าตั้งต้นของตำแหน่ง + ที่เพิ่มให้ − ที่ตัดออก

ระบบเก็บเฉพาะ **ส่วนต่าง** (`users.permissions` = `{grant, revoke}`)
ไม่ใช่รายการสิทธิ์ทั้งชุด — พอแก้ค่าตั้งต้นของตำแหน่งภายหลัง
คนที่ไม่ได้ตั้งข้อยกเว้นจะได้สิทธิ์ใหม่ตามไปด้วยเอง ส่วนคนที่ตัดสิทธิ์นั้นไว้ก็ไม่กลับมา
(มีเทสคุมทั้งสองเคส)

ทำแบบนี้เพราะร้านจริงมีข้อยกเว้นเสมอ เช่น แคชเชียร์อาวุโสคนหนึ่งที่ให้ปิดรอบได้
แต่คนอื่นในตำแหน่งเดียวกันไม่ได้ · บัญชีที่ถูกปิดใช้งานจะเสียทุกสิทธิ์ทันที
และระบบกันไม่ให้เหลือร้านที่ไม่มีเจ้าของเลยสักคน

## ใบสั่งครัว (KDS + สลิป)

**1 ครั้งที่กด "ส่งครัว" = 1 รอบ (round)** ของบิลนั้น
ถ้ารอบนั้นมีทั้งอาหารและเครื่องดื่ม จะแตกเป็น **2 ใบ** ตาม `products.print_group`
(1 = ครัว, 2 = บาร์, 3 = ของหวาน) เพราะครัวกับบาร์อยู่คนละที่และทำคนละคิว

### หน้าจอครัว `/kitchen`

- 3 คอลัมน์: รอทำ → กำลังทำ → รอเสิร์ฟ (กดปุ่มเดียวเลื่อนไปขั้นถัดไป)
- ไฮไลต์อัตโนมัติ: เกิน 15 นาทีขอบเหลือง, เกิน 25 นาทีขอบแดง
- ใบที่มาจากลูกค้าสั่งเองมีป้าย QR กำกับ ครัวจะได้รู้ว่าไม่ได้ผ่านปากพนักงาน
- ดึงข้อมูลใหม่เองทุก 8 วินาที และ**หยุดดึงเมื่อสลับแท็บออกไป** (ประหยัดแบตแท็บเล็ตในครัว)
- กรองตามจุดผลิตได้ — เปิดแท็บเล็ตในครัวค้างที่ `?print_group=1` และบาร์ที่ `?print_group=2`

ตั้งแท็บเล็ตเครื่องเดียวในครัวเปิดหน้านี้ค้างไว้ ก็ใช้แทนเครื่องพิมพ์ได้เลย

### สลิปกระดาษ `/kitchen/tickets/{id}/print`

หน้า HTML กว้าง 80 มม. เปิดหน้าต่างพิมพ์ให้อัตโนมัติ — ใช้กับเครื่องพิมพ์ความร้อนที่ติดตั้งเป็น
printer ปกติของเครื่องได้เลย ไม่ต้องเขียน ESC/POS driver

> อยากได้ ESC/POS แบบส่ง raw command ไปเครื่องพิมพ์ในเครือข่ายโดยตรง (ตัดกระดาษเอง เปิดลิ้นชักเอง)
> ต้องเพิ่ม `mike42/escpos-php` + queue job ยิงไป IP เครื่องพิมพ์ — โครงสร้าง `kitchen_tickets`
> รองรับไว้แล้ว (มี `printed_at`) เหลือแค่ต่อ driver

### เมื่อบิลถูกทำลาย

`OrderService::void()` จะยกเลิกใบสั่งครัวที่ยังค้างอยู่ให้อัตโนมัติ
ครัวจะไม่ทำของที่ไม่มีคนจ่าย

## มาตรฐาน SQL ในโปรเจคนี้

Keyword ตัวใหญ่ทั้งหมด, หนึ่งคอลัมน์ต่อบรรทัด, จุลภาคนำหน้า, ใช้ alias สั้น:

```sql
SELECT o.id
     , o.order_no
     , SUM(oi.line_total) AS total
FROM orders AS o
LEFT JOIN order_items AS oi ON oi.order_id = o.id
WHERE o.status = 'paid'
GROUP BY o.id, o.order_no
```

## สิ่งที่ยังไม่ได้ทำ (ไว้ต่อยอด)

- ESC/POS ยิง raw command ไปเครื่องพิมพ์โดยตรง (ตอนนี้พิมพ์ผ่านเบราว์เซอร์)
- WebSocket (Laravel Reverb) แทน polling — ถ้าร้านใหญ่และต้องการทันทีจริง ๆ
- ตรวจสอบยอดเงินเข้าอัตโนมัติ (ต้องต่อ API ธนาคาร — โดยออกแบบไว้ให้พนักงานยืนยันเอง)
- เดลิเวอรี่ร้านส่งเอง + คิดค่าส่งตามระยะทาง
- ต่อผู้ให้บริการ SMS จริงสำหรับ OTP (โครงสร้างพร้อมแล้ว เหลือเสียบ driver)
- ดึงทะเบียนพนักงานจากระบบ HR อัตโนมัติ (ตอนนี้ HR กดอนุมัติเอง)
- อัปโหลดรูปเมนู (ตอนนี้ `products.image_path` พร้อมแล้ว แต่ยังไม่มีหน้าอัปโหลด)
- โหมดออฟไลน์ / sync เมื่อเน็ตหลุด
- เชื่อม Grab / LINE MAN / ShopeeFood (ตาราง `orders.channel` เตรียมไว้แล้ว)
- รายงานกำไรขั้นต้นแยกรายสินค้า
